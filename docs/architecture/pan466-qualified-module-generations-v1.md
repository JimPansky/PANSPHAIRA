# Qualified module generations — LIFE-06

This additive adapter composes the accepted PAN464 fixed retained PostgreSQL /
Superset controller. It is not a new scheduler, grant service, installation
controller or generic updater. The advisory pilot module graph still does not
cover the whole repository.

## Descriptor and actual CLI preflight

The existing module descriptor may carry one closed optional `lifecycle` object:
state content/config/derived/authority paths, migration identity and source/target
versions, exact direct consumers, and APPEND_ONLY / REVALIDATE_CURRENT recovery.
Malformed, incomplete or unknown direct-consumer declarations fail closed.

`node scripts/module-contribution.mjs lifecycle-check --base <retained-commit> --state-root <independently-retained-state>`

reads actual Git-visible changes and the separately supplied prior migration and
local configuration state. Changed unowned files remain uncovered. A migration
ID cannot describe different implementation bytes or a different edge, including
when it was retained as applied history after disappearing from a later descriptor.
Configuration is a three-way proposal: conflicts preserve local/history bytes.
Derived indexes require matching content/config/semantic/authority generations;
unknown or stale indexes hold rather than being relabeled as compatible.
Protected authority surfaces and fields cannot regain old qualification merely
by being called content. Only bounded already-owned small documentation changes
with unchanged semantic/state bindings may take the nonsemantic preflight path.
Measured work is scoped file/byte reads and zero native dispatch/migration/rebuild,
not a promised whole-pipeline speedup.

Every CLI result remains CHECK_ONLY / authority NONE / automaticUpdateCoverage
false. A plan, eligible preflight or successful selected test never grants an
effect. Configuration proposals are not applied by this command.

## One exact native module-use entry

`createQualifiedRetainedModuleV1` accepts trusted owner inputs: a captured module
binding, current module and independent existing native permission readers,
separate scoped historical-read permission, and the accepted exact native options.
The closed module identity binds current target code, the fixed consumer commit,
qualification image and the explicit module generation. Arbitrary descriptor
hashes, consumer substitutions or caller `eligible` flags are not qualification.

The adapter executes the actual accepted paired runner before retaining its
qualification digest. Native effects still run only through the existing PAN464
controller, its fixed commands/mounts, independent protected business oracle,
checkpoint/admission, durable ownership and STOP/REVOKE handling. The injected
current-module guard is reread at each native authority invocation and immediately
before protected starts. Existing direct PAN464 APIs do not thereby acquire a
universal module-lifecycle contract.

Module generation and native database/schema/content generations are separate
axes. Historical records retain observed source, activation and new-write rows
and consumer readback; they do not replace observations with expected rows.
History requires a fresh independent PAN466_SYNTHETIC_HISTORY read scope and
expiry. Historical read does not mint a new write grant, make stale content
current, erase newer work or replay/restore a held operation. Its owned local
self-digests are not signatures or hostile-host integrity guarantees.

## Required native qualification

The required entry is `npm run pan466:native -- --output <outside-source-summary>`.
It requires Linux x64 Node24.19.0/ABI137, the exact retained PAN source
`c255df512ba86cf8c346c797bac5400bac1b6ab3`, consumer
`72d9a4af87fbbc5b23cb52835cd2f85415b8ddc7`, a clean exact target checkout,
the already documented pinned PAN464 native image, and an explicitly owned
synthetic scratch directory. Missing prerequisites fail; none are optional skips.

Set EXPECTED_PAN_HEAD, PAN466_SOURCE_ROOT, PAN466_KS_ROOT, PAN466_IMAGE_ID and
PAN466_OWNED_ROOT to the admitted values. The source/consumer and native image
preparation remain the accepted Retained Native Pair workflow; this adapter does
not download arbitrary versions or mint production permission.

The focused gate uses one separate live actor and independently parent-owned
current module/write-permission/history-permission files. At actual durable
POST_ACTIVATION_WRITE_INTENT it waits for typed IPC, preserving the same PID and
captured generation. The owner changes current facts during that wait, then
resumes the actor through the real protected native write entry.

Required scenarios:

- Current compatible separately authorized native new write, verified with the
  existing independent producer/consumer business oracle.
- Changed current module generation with write permission otherwise retained:
  stale write holds before native starts; retained data, checkpoint and completion
  logs remain unchanged and actual historical content remains readable.
- Actual revoked native write grant with compatibility otherwise retained:
  permission denial, no new native write, history still under separate read scope.
- Both generation change and revocation: history remains readable and new write
  denies; the preceding separate negatives independently establish both checks.
- Fresh compatible generation binding on another newly qualified retained fixture
  with independently authorized current permission: actual native new write.

The execution emits only a source-bound sanitized summary. Raw native stores,
synthetic grants, keys, history and internal logs remain in owned private scratch;
do not publish the directory wholesale. Source code/test instructions and a
successful local summary are not independent acceptance, hosted CI, merge,
release or public artifact readback. Those remain separate hard delivery gates.

## Limits and companion navigation fix

Only the exact isolated synthetic pair and this explicit entry are claimed.
Docker Unix-socket authority remains trusted host authority; network isolation
is not a complete host sandbox. No production/customer effects, arbitrary pairs,
generic process scheduling, offhost backup, PKI or power-loss guarantee is added.
The IPC wait is cooperative deferred execution, not OS suspension or power loss.

The expressly authorized PAN442-R1-INTEGRATION-ANCHOR-01 companion adds only a
stable compatible assurance target and built-target regression for the three
existing secondary routes. Root README bytes/design and all security/nonclaims
remain unchanged. The already delivered README release and PAN431 closure are
not respun; this small fix is delivered jointly with the next fitting functional
candidate only after that candidate's actual remaining gates.
