# P08 deterministic material proposals

This is the bounded source-evidence material-planning core for PAN #522.
It imports the existing compiled P01 stock contract. It does not replace the
leading order, stock or procurement store and has no dispatch operation.
Use only synthetic or explicitly authorized snapshots. The included
PAN-MATERIAL reference is separate from COMMON-TRADE-01; no common-reference
or external-provider qualification is inferred from it.

## Operator and build

Install the exact repository lock with `npm ci --ignore-scripts`, then
`npm run build`. The source operator runs as follows:

    node scripts/run-pan522-material-plan.mjs plan --input tests/fixtures/pan522/pan-material-reference-v1.json
    node scripts/run-pan522-material-plan.mjs disabled
    npm run pan522:test

`plan` accepts exactly one explicit JSON file. The file must be regular,
not a symlink, and at most 262144 bytes. `disabled` reads no input file.
Execution, role, target, qualification and test-filter selectors are denied.
The canonical suite requires the existing owned TMPDIR or an explicitly
provided owned RUNNER_TEMP; it never falls back to a system temporary path.

## Closed snapshot contract

`pansphaira.pan522/material-plan-input/v1` contains asOf, horizonEnd,
calendars, items, effective BOM versions, distinct demands, explicit stock
and dated receipts. Unknown keys, getters, proxies, non-plain records and
non-data values are rejected before planner reads. Input is not mutated.
A canonical SHA256 inputDigest binds the exact supplied snapshot, including
array order; sorted proposal semantics do not fabricate another input's
provenance. stockContractDigest binds the actual existing stock evaluation.

The current scope is integer STK quantities, UTC day dates in 2000–2099,
a horizon no longer than 366 days, at most 64 items, at most 128 rows per
input family, positive lot multiples and non-negative lot minima/safety
floors. All input and derived quantities are bounded to 1000000000.
Total root and derived pegging requirements are bounded to 4096. Overflow
or a larger expansion fails closed rather than truncating allocations.
Every item has one explicit dated stock row and calendar. Native stock
position aliases remain rejected by the existing stock contract.

## Algorithm and explainability

Physical stock minus reserved and blocked stock is evaluated through the
existing P01 stock contract. Finished-goods usable stock is netted before
BOM explosion. A safety floor is retained; shortages include a deficient
floor and are rounded using the declared lot minimum and multiple.
Only CONFIRMED receipts due by a requirement date cover it, once per receipt
ID. UNKNOWN and later receipts remain explicit exclusions, not safe supply.
Receipt confirmation in a caller snapshot is not external-target proof.

Every parent contributes its requirements before any component is netted.
Within each item, all requirements are grouped by need date and processed
chronologically. This prevents root ordering from allocating stock to a
later component need before an earlier component need generated by another
root. One proposal per item/date has an unambiguous ID and includes every
quantity-bearing requirementAllocation and plannedAllocation. Coverage uses
stable FIFO requirement order. Safety/lot surplus is separately labeled,
with null rootDemandId and its actual ancestor rootDemandIds; it is never
invented as another demand. Derived requirements bind the parent proposal,
source requirement, selected BOM version and component quantity.

MAKE items explode the calculated parent lot, not the raw root demand.
BOM validity is [validFrom, validUntil), selected at the parent's calculated
release date. Overlapping versions, cycles in the union of declared BOM
edges, duplicate demand IDs and wrong units fail before stock can hide the
invalid contract. Declared calendars provide working weekdays and holidays;
leadWorkdays count strictly preceding working dates. Requirement/release
scheduling cannot leave the selected calendar's validity window.

The reference ten KIT yields A20/B30 gross, A15/B30 planned, component need
2026-10-12, releases 2026-10-07 and 2026-10-08. Two distinct ten-KIT demands
on that date aggregate KIT20, A40/B60 gross and A35/B60 planned, retaining
both roots and every allocation. Product tests cover multilevel versions,
safety/lot quantities, confirmed/late/unknown receipts and chronological
component needs. Independent integer/date expected-value evidence is kept
in the private delivery receipts, not presented as external-source proof.

## Authority, capacity and rollback

`MATERIAL_PROPOSALS_ONLY` is data, not a grant. executionAuthorized and
capacityQualified are always false. A material release/need date is not a
finite-capacity result, feasible production schedule or delivery promise;
no automatic capacity, order, stock or purchase transition exists here.
The actual native no-effects test compares retained orders, stock and
movement history before/after and rejects a copied result as a native grant.

`materialProposalView(input, 'DISABLED')` or the `disabled` operator returns
`MATERIAL_PROPOSALS_DISABLED` with no proposals. It changes only this new
view. Existing native order transitions remain enabled; no leading store,
historical movement, prior qualified generation or global setting changes.
The function's enabled mode delegates to the same tested planner. An unknown
mode fails closed. Source-evidence delivery requires fresh build/run of the
exact archives; it is not a turnkey runnable package or productive permission.
